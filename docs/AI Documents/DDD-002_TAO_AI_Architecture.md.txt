# TAO Design Discussion Document

# DDD-002 – TAO AI Architecture

Version: 1.0

Status: Approved for MVP

Last Updated: 2026-07-22

---

# 1. Purpose

This document defines the architectural principles, responsibilities, project structure and design decisions for all AI capabilities within TAO.

The objective is to establish a single reusable AI architecture that can be used across every module while remaining provider-agnostic and easy to evolve.

This document is intentionally implementation-oriented and complements the Functional Requirements (FR) and Software Design Documents (SDD).

---

# 2. Vision

TAO is not simply a recruitment platform that uses AI.

TAO is an AI-powered recruitment platform.

Every major module will eventually rely on AI.

Examples

- Job Profile Generation
- Resume Matching
- Hiring Strategy
- Assessment Strategy
- Question Generation
- Candidate Evaluation
- Assessment Reports
- TAO Coach

Rather than allowing every feature to implement AI independently, TAO provides a dedicated AI architecture.

---

# 3. Design Principles

| Principle | Decision |
|------------|----------|
| AI is a platform capability | Shared across all modules |
| Provider independence | Business logic never depends on Ollama/OpenAI |
| Vertical Slice | AI organized by business capability |
| Business-first | AI produces business artifacts |
| Prompt-driven | Prompt templates remain version controlled |
| Human supervision | AI generates, humans approve |
| Simple MVP | No unnecessary frameworks |

---

# 4. Why TAO.AI Exists

The AI implementation should not live inside the Application project.

Reasons

- Prevent duplicated prompt builders.
- Centralize AI response validation.
- Centralize prompt management.
- Centralize AI orchestration.
- Reduce future refactoring.
- Keep Application focused on business workflows.

---

# 10. Prompt Strategy

Prompt templates are stored as Markdown files.

Example

```
Prompts
    JobProfilePrompt.md
```

Reasons

- Git versioning
- Easy review
- Product readable
- Future Prompt Management

Prompt templates are NOT embedded inside code.

---

# 11. AI Pipeline

Every AI feature follows the same pipeline.

```
Business Request
        │
        ▼
Prompt Builder
        │
        ▼
Prompt Template
        │
        ▼
LLM Provider
        │
        ▼
Raw Response
        │
        ▼
Response Parser
        │
        ▼
Response Validator
        │
        ▼
Business Result
```

No business code should process raw LLM responses.

---

# 12. AI Response Validation

Every AI response must be validated.

Validation includes

- Required properties exist
- JSON is valid
- Business structure is valid
- Required sections are generated

Invalid AI output is rejected.

The Application layer never receives malformed AI responses.

---

# 13. Business Results

AI returns business-ready objects.

Example

JobProfileGenerationResult

Contains

- Prompt
- RawResponse
- ProviderName
- ModelName
- PromptVersion
- GeneratedContent
- StructuredProfile

Application handlers never receive raw LLM responses.

---

# 14. Application Handler Responsibilities

Application handlers should only

- Load aggregates
- Validate business rules
- Invoke AI generator
- Create/update aggregates
- Persist
- Return Result

Application handlers never

- Build prompts
- Parse JSON
- Validate AI output
- Communicate with providers

---

# 15. Provider Independence

The provider is hidden behind abstractions.

```
JobProfileGenerator
        │
        ▼
ILLMProvider
        │
        ▼
OllamaProvider
```

Future providers

- OpenAI
- Azure OpenAI
- Claude
- Gemini

No Application changes required.

# 20. Final MVP Decisions

✅ Introduce TAO.AI project now.

✅ Organize AI by business capability.

✅ Keep provider implementations in Infrastructure.

✅ Store prompts as Markdown files.

✅ Validate every AI response.

✅ Application never processes raw AI responses.

✅ AI returns business-ready models.

✅ Provider independent architecture.

✅ Every future AI module follows the same pipeline.
